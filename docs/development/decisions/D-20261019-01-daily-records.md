# D-20261019-01：按天组织开发记录

日期：2026-10-19。状态：accepted。范围：开发文档组织。

## 背景

项目已有大量训练、调研与诊断文档，首页曾混入长篇历史实验流水账。
需要同时回答“现在做到哪”和“某天为什么这么做”，并避免维护一张不断增长的 CSV 总表。

## 决定与依据

用户明确选择按天拆分、多个短 CSV 配合 Markdown 的方式。

- 目录为 `docs/development/YYYY/MM/DD/`，日期按 Asia/Shanghai 记录。
- changes、tasks、experiments 分表，模块作为字段；无相应活动时不创建空表。
- 单表最多 50 条数据行，字段保持简短，超出按专题与分片拆开。
- 当日 README 保存背景和结果，STATUS 保存当前快照，ROADMAP 保存近期跨天任务。
- 既有实验报告不迁移，CSV 仅索引；事实、计划、验证与默认配置变更分别说明。

## 考虑过的方案

| 方案 | 处理 |
| --- | --- |
| 单一 CSV 全局台账 | 不采用，后续过长、字段混杂 |
| 模块／月份作为主目录 | 本次不采用，同一天跨模块工作更适合集中回看 |
| 立即建设网页管理系统 | 暂缓，先用 Git 可读文件验证维护方式 |

## 影响与验证

此方案便于日常追加、GitHub 阅读和按模块筛选。跨天任务需保持原 ID，当前状态与历史进展
分别维护；这是持续维护成本，不能仅靠建目录解决。

首日记录、模板与文档导航随实现提交；检查 CSV 结构、状态、相对链接和 Markdown 链接。
模型、checkpoint、训练数据和默认配置均不因本决定改变。

## 重新考虑条件

若日文件规模导致检索困难，优先增加自动索引或只读看板。若台账与原始报告频繁失配，
先增加一致性检查，避免继续人工复制指标。后续方案替代本决定时追加链接并保留本记录。
