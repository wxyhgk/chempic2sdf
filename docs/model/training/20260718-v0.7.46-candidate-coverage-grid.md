# v0.7.46 候选覆盖阈值与容量网格

## 目标

v0.7.44 的逐点审计显示，v0.7.43 的 454 个部署漏点中有 203 个在 6px 内没有正确
角色候选。本轮不训练 selector，只判断降低隐式候选阈值或扩大总候选容量，是否能以
合理成本提高 Candidate Oracle 上限。

评测使用 validation 498 张、16,922 个真实顶点。文字候选阈值固定 0.05，隐式候选
比较 0.05 和 0.02，总容量比较 256 和 384。MR-TADF 不参与评测或阈值选择。

## 协议修正

旧 Candidate Oracle 脚本分别截断文字和隐式候选，合并后可能超过声明容量。本轮修复
为与训练/推理一致的协议：

```text
文字候选按分数优先占用总容量
    -> 隐式候选填充剩余位置
    -> 总候选数不超过 256 或 384
```

评测同时新增：

- 一对一覆盖缺失顶点数；
- 有覆盖缺失的图片数；
- 平均与最大候选数；
- 容量饱和图片数；
- 平均全点对数量。

端到端审计的 `candidate_available` 是“该原子附近是否至少存在一个同角色候选”；本轮
Candidate Oracle 使用一对一分配，因此还会额外计入多个原子竞争同一候选的覆盖冲突。
这解释了部署审计的 203 与本轮基线 212 之间的 9 个差异。

## 结果

| 隐式阈值 / 总容量 | 平均候选 | 平均点对 | 相对点对成本 | 缺失顶点 | 缺失图片 | Oracle exact |
|---|---:|---:|---:|---:|---:|---:|
| 0.05 / 256 | 125.42 | 9,084 | 1.00× | 212 | 66 | 86.75% |
| 0.05 / 384 | 126.76 | 9,457 | 1.04× | 212 | 66 | 86.75% |
| 0.02 / 256 | 240.84 | 29,316 | 3.23× | 210 | 65 | 86.95% |
| 0.02 / 384 | 280.58 | 40,972 | 4.51× | 209 | 65 | 86.95% |

具体结论：

- 单独扩大到 384 没有找回任何真实顶点，说明 0.05 下主要不是容量截断；
- 降阈值到 0.02 后，k256 只找回 2 个顶点和 1 张 Oracle exact 图片；
- 0.02/k384 再找回 1 个顶点，但没有增加整图 Oracle exact；
- 0.02/k256 有 337/498 张达到 256 容量上限，训练点对成本增加到 3.23 倍；
- 0.02/k384 平均点对成本达到基线 4.51 倍。

## 决策

- `0.02` 隐式阈值：覆盖收益不足，NO-GO；
- 384 总候选容量：没有整图 Oracle 收益，NO-GO；
- 不进入更大候选池 selector 训练，不改变 0.05/256 生产协议；
- 不通过 3.2 到 4.5 倍全点对成本换取 1 张 Oracle exact；
- 212 个一对一覆盖缺口主要来自候选头本身，而不是阈值或容量截断；
- 下一步需要改候选生成监督或增加新的候选来源，而不是继续降低阈值。
