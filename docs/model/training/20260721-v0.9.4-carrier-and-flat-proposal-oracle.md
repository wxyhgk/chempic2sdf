# v0.9.4 Carrier 与 Flat Proposal Oracle

> 状态：capacity100 受控实验完成；direct carrier 坐标重预测路线正式 NO-GO
>
> 下一阶段：v0.9.5 冻结 flat proposal 坐标，只学习键组分组、类型和成员数
>
> 数据边界：只使用 train-only capacity100；`internal_test` 未读取、未训练、未评估
>
> 生产推理：保持 `v0.7.10`，本实验没有接入前端或生产模型

## 本轮要回答的问题

v0.9.3 已经证明 canonical absolute-member head 不适合作为键组内部表示。v0.9.4 因此把
一个可见键符号压缩成 typed carrier：模型只预测少量语义控制点和类型参数，再由确定性
几何函数展开为精确物理 members。

本轮需要区分两个问题：

1. carrier 协议能否无损表达 `single_line`、双/三平行线、虚楔键和实楔键；
2. 是否应该让新的 group query 从栅格图重新预测一套 carrier 坐标。

第一个问题在 codec roundtrip 中已经通过。第二个问题必须由 direct carrier 与
flat-proposal oracle 的受控对照回答。

## Typed Carrier 表示

实现入口：

```text
chemvector/bond_group_carrier_geometry.py
chemvector/bond_group_carrier_set.py
chemvector/bond_group_carrier_set_data.py
chemvector/train_bond_group_carrier_set.py
chemvector/evaluate_bond_group_carrier_set.py
```

外层仍是 192 个无序对象 query。每个 bond group 不再输出 `max_members x 8` 个绝对坐标，
而是输出：

- 最多 4 个 carrier 控制点，共 8 个坐标；
- 最多 2 个正值参数，例如三线间距或虚楔键首末半宽；
- group stroke；
- group type 和 member count；
- text box 继续使用独立 bbox 几何。

确定性展开规则包括：

- `single_line`：两个端点直接形成一条线；
- `parallel_2`：四个控制点直接表示两条物理线；
- `parallel_3`：中心线加半间距展开三条线；
- `hashed_wedge`：中心轴、首末半宽和 member count 展开短线序列；
- `solid_triangle/solid_quad`：有序多边形控制点。

codec 支持端点反向、平行线交换、虚楔宽度交换和多边形循环/反向等价。协议本身不是本轮
NO-GO 对象；NO-GO 的是从栅格图重新回归这些坐标的 direct carrier predictor。

## Direct Carrier 训练

direct carrier 从 v0.9.3 full7k group checkpoint 初始化：

```text
outputs/checkpoints/chemvector-v093-bond-group-set-capacity100-cold-full-step7000/
  step-007000.pt
```

目标模型配置：

```text
queries                = 192
max_members            = 143
local_query_kernel     = 5
endpoint_refine_kernel = 25
image_size             = 768
```

carrier 几何头、正值参数头、group stroke 和 endpoint refiner 可训练；外层视觉编码器、
decoder、type/count/text 路径继承并冻结。训练 500 step，batch size 为 2，共看到 1,000 个
样本实例。

主 checkpoint：

```text
outputs/checkpoints/chemvector-v094-bond-group-carrier-set-capacity100-geometry-step500/
  step-000500.pt
```

主评估采用 count-head decode。结果为：

| 指标 | direct carrier step500 |
|---|---:|
| member line recall@8q | **4.92%** |
| member line recall@32q | **55.69%** |
| Bond IoU | **17.95%** |
| group-set exact | 0% |
| flatten exact | 0% |
| invalid samples | 3 |

模型并不是完全没有学到对象语义：

- 总对象 count exact 为 100%；
- Hungarian matched type accuracy 为 99.78%；
- matched raw member-count accuracy 为 99.93%；
- 但 type-count set exact 只有 17%。

因此主要失败不是“完全数不出对象”或“完全分不出类型”，而是坐标精度不足。

## Direct Carrier 几何取证

对 matched query 拆解 coarse 与 refined carrier 后得到：

| 类型 | coarse 最大控制点误差 p50 | refined p50 | refined r@8q |
|---|---:|---:|---:|
| `single_line` | 102.31q | 19.93q | 8.94% |
| `parallel_2` | 144.60q | 36.77q | 0.12% |

`parallel_2` 不是只有第二条线失败：

| member | 最大端点误差 p50 | r@8q |
|---|---:|---:|
| 第一条线 | 26.22q | 1.50% |
| 第二条线 | 32.34q | 1.61% |

两条线都远离 8q 容差。第二条线略差，但不是决定性异常。`single_line` 的两个端点各自
p50 约为 13.6q；完整对象要求两个端点同时落入 8q，所以 matched-query object recall 也
只有 8.94%。count-head selector 保留约 93.53% 的 Hungarian matched query，selector 是
后续问题，但不能解释当前从 85% 级别跌到 5% 的几何差距。

外层 assignment 也没有发生训练震荡：

- step250 到 step500 的 target-query 映射保持率为 99.31%；
- coarse 与 refined assignment 保持率为 89.71%。

三处 invalid 都是 `solid_quad` 自交。carrier codec 能正常展开，错误来自四个多边形点的
独立坐标回归缺少 simple-polygon 约束。这是 direct coordinate head 的另一个症状，不是
typed carrier 展开公式错误。

## Flat Proposal Oracle 设计

oracle audit 不训练新模型。它读取已完成的 flat primitive-set 预测：

```text
outputs/checkpoints/chemvector-v092-primitive-set-capacity100-endpoint-only-lr1e5-step11000/
  step-011000.pt

outputs/evaluations/chemvector-v092-primitive-set-capacity100-endpoint-only-lr1e5-step11000-eval/
  predictions.jsonl
```

oracle 只提供：

- GT group count；
- GT group type；
- GT physical-member partition，仅用于 proposal association。

oracle **不把 GT 坐标写入输出**。输出坐标全部来自 flat predictor：

- 同类型 proposal 先做一对一 Hungarian association；
- 超过 association tolerance 的 proposal 被丢弃；
- 缺失 member 不使用 GT 坐标补齐，而是保留 invalid group slot；
- `parallel_2` 必须同时找到两条线；
- `parallel_3` 必须找到全部三条线；
- `hashed_wedge` 至少需要两条已匹配短线，再拟合 carrier 并按 GT member count 展开。

因此 oracle 不是可部署模型，也不能证明分组问题已经解决。它回答的是：如果只把“哪些
已预测物理图元属于同一组”解决，现有 flat 坐标还剩多少可用能力。

实现与产物：

```text
chemvector/audit_flat_proposal_carrier.py
outputs/evaluations/chemvector-v094-flat-proposal-carrier-oracle-capacity100/
  oracle_metrics.json
```

## Flat + Oracle 结果

正式对比采用 32q association tolerance。该 tolerance 只控制 proposal 是否允许进入当前
GT group，不改变最终 evaluator 的 8q/32q 几何判定，也不允许 GT 坐标回填。

| 路线 | line r@8q | line r@32q | Bond IoU |
|---|---:|---:|---:|
| direct carrier step500 | **4.92%** | **55.69%** | **17.95%** |
| flat primitive-set 原始几何 | 85.45% | 92.99% | 66.88% |
| flat proposal + oracle grouping | **85.54%** | **96.18%** | **70.62%** |

oracle grouping 没有重新预测坐标，却保留并略微提升了 flat 的几何结果。32q association 下
的分类型 group coverage 为：

| group | oracle group recall |
|---|---:|
| `single_line` | 97.84% |
| `parallel_2` | 95.05% |
| `parallel_3` | 81.25% |
| `hashed_wedge` | 78.21% |
| `solid_triangle` | 83.56% |
| `solid_quad` | 100.00% |

text-box recall 仍只有 2.87%，说明文字框/OCR 是独立未解决分支；它不改变本轮关于 bond
坐标和 group partition 的结论。oracle 中的 object/type/member count 100% 来自审计授予的
GT group 信息，不能当作学习指标。缺失 proposal 被明确保留为 invalid slot，所以
`oracle_metrics.json` 中的 invalid 数量也不能与生产 decode 的 invalid 直接比较。

## 为什么主因不是数据量

direct carrier、flat baseline 和 oracle 使用完全相同的 100 张 capacity 图。若图像或标签
没有足够信息，flat predictor 不可能在同一批图上达到 85.45% r@8q 和 66.88% Bond IoU。

oracle 进一步证明，当前 flat 输出中已经存在可达到 85.54% r@8q、96.18% r@32q 和
70.62% Bond IoU 的物理坐标。缺失的主要变量是 group association/partition，不是更多
图片才能提供的新坐标证据。

这不表示 100 张数据足以证明泛化；它只说明 capacity100 失败不能归因于数据量。应先让
新架构保留同一批数据上已经解决的能力，再扩到 pilot、正式 validation 和公开 benchmark。

## 为什么不再把“多训练几步”作为主线

direct carrier 只训练了 500 step，继续训练可能继续降低它的回归误差。但这不是决定架构
方向的充分理由：

1. direct carrier 主动丢弃了 flat 已经达到 85% r@8q 的坐标，并从低精度 v0.9.3 group
   checkpoint 重新学习坐标；
2. oracle 不增加训练步数、不使用 GT 输出坐标，只增加正确分组，立即恢复到 85.54%；
3. direct carrier 的 count/type/member-count 已接近饱和，继续优化的主要成本仍会花在重复
   学习一项已经由 flat predictor 解决的任务上；
4. 即使长训最终追平 flat，也只是更昂贵地重新获得原有能力，不能证明 direct coordinate
   regression 是合理拆分。

所以这里的判断不是“500 step 永远不可能收敛”，而是“没有必要把下一阶段预算继续投入
到重新预测坐标”。oracle 已经给出更直接、可验证且保留现有能力的分解。

## 正式判定

v0.9.4 的正式结论：

```text
Raster -> group query -> direct carrier coordinate regression

NO-GO
```

NO-GO 范围只包括 direct carrier predictor。以下资产继续保留：

- Visual SVG v0.2 外部协议；
- typed carrier/envelope 内部编码；
- carrier 到精确 physical members 的确定性展开；
- group 作为一等视觉对象；
- flat primitive-set 的物理坐标提议能力。

## v0.9.5 路线

v0.9.5 固定为：

```text
Raster
  -> frozen flat primitive proposals + frozen exact coordinates
  -> learned proposal keep / group membership / group type / member count
  -> deterministic carrier fitting
  -> Visual SVG v0.2
```

训练时坐标 tensor 必须 detach，并且 flat geometry、endpoint refiner 和 stroke geometry 不进入
optimizer。新模型只学习：

- 哪些 proposal 是真实物理图元；
- 哪些 proposal 属于同一个 bond group；
- group 的视觉类型；
- `hashed_wedge` 等可变 group 的 member count；
- 必要的 proposal/group confidence 与 no-object 判定。

不再加入 carrier coordinate loss、member coordinate loss 或新的 endpoint regression。
carrier 参数由选中的固定 proposal 确定性拟合。这样双键、三键和虚楔键的分组错误可以
获得梯度，同时不会破坏 flat 坐标精度。

v0.9.5 的第一门控仍在 capacity100 完成。最低要求是：

- 固定坐标后的 line r@8q 不低于 80%；
- line r@32q 不低于 90%；
- Bond IoU 不低于 65%；
- 单/双/三线和虚楔键必须分别报告 proposal coverage 与 learned group recall；
- oracle 信息只能用于上限审计，不能进入模型输入或 checkpoint 选择；
- `internal_test` 继续封存。
