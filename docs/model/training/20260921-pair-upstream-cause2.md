# 缺腈基碳与 C→F 的定位结果

## 结论

针对上轮固定两张训练图，完成 **1 次冻结结构模型 CPU 前向、2 批冻结 OCR 前向（共 17 个裁剪）**。
没有训练、梯度、GPU、模型/阈值/生产配置修改，也没有读取开发样本或封存测试。

1. **腈基碳：同一冻结 initial 的 CPU 回放中，原始候选存在，是 selector 把两个合格候选都筛掉了。**
2. **C→F：实际 OCR 裁剪包含完整 C，不是字符被截断；同一 OCR 改用源字形框加 4px 边缘可识别成 C。**
   贴紧字形、去掉边缘反而识别成 N。因此定位为裁剪与识别器之间的敏感性问题，不能简单归因于缺字，
   也不能说识别器本身没有鲁棒性问题。

这是两个具体病例的机制定位，不是已修复模型或已经提高整图准确率。

## 1. 腈基碳到底在哪丢的

样本：`curr_08d02946e879406f__font_large`，目标 T5，源位置约 `(415.02, 499.67)`。

回放使用原始 PNG 和 SHA 固定的 initial；模型 `eval + no_grad + requires_grad=False`。
先保存全部 128 个原始候选及 selector 得分，再读源标注做距离分析。
最终 17 个入选候选的 ID 与 q1023 坐标，均复现原 pair 试训的 initial 保存结果。
这是**离散选点结果一致**，不是声称 CPU 浮点张量与当时 GPU 缓存逐位相等。

| CPU 回放候选 | 距 T5，直接坐标距离 | 原始热图分数 | selector 预评分 | selector 修正项 | 最终评分 | 结果 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| P20，网格 24296 | 5.880px | 0.2145 | -0.8567 | -0.2071 | -1.0639 | 拒绝 |
| P22，网格 23911 | 3.019px | 0.1962 | -1.0372 | -0.7963 | -1.8335 | 拒绝 |

原始候选门槛为 **0.01**，二者均通过局部峰值、top-k、原始分数筛选，且均在原 6px 半径内。
selector 的保留门槛为 **-0.25**，二者均未达到。

因此不是这处碳在 dense detector 中完全没有响应，也不是 top-k 没留容量，
更不是后续 pair 连键头删了原子；在这里，丢点发生于 **原始候选 → selector 保留集合**。
注意 selector 的预评分已经低于门槛，修正项又进一步降低，不能只怪后面的关系修正项。

只读复核当前的一对一监督代码和这次保存的 CPU 候选后，T5 分配给 P22；P20 没有目标分配。
也就是说两个在几何容差内的候选中，一个作正例，另一个未匹配候选在原 selector presence 监督中作负例。
而推理时，两者最后都没保留。这反映出“逐候选的一对一监督”与“一个原子至少保留一个有效候选”之间的区别。
**这不是本轮测得的历史训练梯度因果关系**，不能据此断言某个 loss 项就是全部根因。

该只读匹配复核按现有 FP32 `torch.cdist` 得到距离约 5.876 / 3.012px，与直接坐标差的微小数值区别
不影响二者都在 6px 内，也不改变本轮任何匹配门槛。回放候选编号仅属于这次保存的明确 lineage。

修复验收应该要求：保留 T5 的一个有效候选，同时不把三键两侧的线段端点/重复候选也保留下来。
本轮没有通过降低全局 selector 阈值或注入真值原子来制造恢复结果。

## 2. C→F：是不是裁剪截掉了 C

样本：`curr_4ef506af64e8f0b8__bond_short`，T39 对应历史 P38。

实际调用链：`FrozenOCRPredictor.from_structure → crop_tensor → bbox_crop(context=4)`。
这里的 4px context 必须算进去，保存框本身不是最终送给 OCR 的全部范围。

| 框的含义 | 原图像素范围 |
| --- | --- |
| 预测浮点框 | `(404.135, 327.292, 420.052, 347.597)` |
| 实际加 4px、PIL 取整后的裁剪 | **`(400, 323, 424, 352)`** |
| 源标注的完整 C 字形框 | `(406, 328, 421, 346)` |

实际裁剪完整包含字形。若只检查未加边缘的预测框，会因为右边少约 1px 而错误判断“C 被裁掉了”。

同一冻结 OCR、同一原图的事先固定对照结果如下：

| 输入裁剪 | T39 输出 | 邻近另一个可见 C（T38）输出 |
| --- | --- | --- |
| 实际预测框 + 4px | **F**，复现历史输出 | 历史未通过文字角色门控，没调用 OCR |
| 源字形框 + 4px，真值诊断对照 | **C** | **C** |
| 源字形框 + 0px，真值诊断对照 | **N** | **N** |

桥环图全部 **13 个历史实际 OCR 裁剪的文字输出都在 CPU 重现**。
T39 的实际裁剪由 24×29 像素变为源框+4px 的 23×26 像素后，归一化缩放、字形位置与周边线段均发生变化，
识别从 F 变 C。去掉全部边缘得到 15×18 的紧框，经过相同 192×48 预处理后反而读成 N。

因此可以确认：冻结 OCR 在合适裁剪下能读出这两个 C；当前接口对小范围裁剪/缩放变化敏感。
**尚不能分离“字形尺度、位置、周边键线”各自的独立贡献**，也不能把“采用真值框成功”当成已可部署的修复。
本轮没有扫裁剪参数，没有选择最佳框替换正式输出，更没有按价态强制把 F 改成 C。

T38 的对照只说明 OCR 能识别它的字形。历史角色头把它当作 IMPLICIT，未送入 OCR；
仅靠改善已进入 OCR 的框，并不能修复这类文字角色漏路由。

## 3. 下一步应改哪里

- **候选侧**：优先验证“同一个局部原子至少保留一个代表”的保留机制，并同时检查三键线条碎片、
  重复点和原有正确点。不能只优化候选平均分类损失，也不能全局降门槛后只看召回率。
- **文字侧**：优先检查/统一 bbox→crop→resize 接口，并把裁剪变化导致 C/F/N 分歧纳入回归。
  分歧应作为不确定性信号，而不是直接根据化学规则覆盖字符；不建议马上重新训练 OCR。
- **连键侧**：等上游责任边界明确后，再单独处理 B2 双键错型和新增假边。
  冻结上游仅训练 pair，无法召回已被筛掉的 T5，也改不了 C→F。

以上是建议，没有开始新的修复、训练或参数搜索。
