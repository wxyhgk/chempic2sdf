# v0.9.25 多节点组件 Oracle OOF

> 状态：target-aware 容量审计完成，组件路线容量 GO；这不是可部署模型或 checkpoint。

## 问题拆分

固定 `min(v0.9.19,v0.9.20)` 的 19 个 cross 中：

- 9 个位于 2 anchors / 1 edge 的孤立组件；
- 10 个位于 3–6 anchors 的多节点组件。

v0.9.24 已证明“看见邻域后仍逐 pair 分类”不够。本轮不训练，只回答一个更严格的问题：如果多节点
组件的联合选择完全正确，而孤立 pair 保持 v0.9.23 原样，理论上能提升多少？

## 协议

候选 pair 图以 anchor 为节点、pair candidate 为边，按共享 anchor 建 connected component。
组件划分只读取 `pair_indices`，不读取标签。仅在 `anchor_count > 2` 的组件内执行标签 oracle：

```text
positive pair -> tau + 1
negative pair -> tau - 1
isolated component -> 保留 v0.9.23 score
```

随后仍调用同一个确定性 maximum-weight matching 和同一套结构指标。审计覆盖：

```text
23,704 multi-anchor components
97,617 pair candidates in those components
7,200 OOF images
```

## 正式结果

| 指标 | v0.9.23 profile | multi-component oracle | full label oracle |
| --- | ---: | ---: | ---: |
| selected cross | 16 | 8 | 0 |
| M2 recall | 99.64116% | 99.83265% | 99.94245% |
| pairable exact | 96.39979% | 98.38848% | 100% |
| parallel-2 violations | 1 | 0 | 0 |
| support lost | 21 | 11 | 0 |
| selected pair precision | 99.99489% | 99.99746% | 100% |

组件 oracle 在完全不改孤立 pair 的条件下将 cross 减半，并同时提升 M2、exact、parallel preservation
和 support。完整标签 oracle 再次达到 cross 0 / pairable exact 100%，说明 candidate pool 仍然足够。

本审计为速度关闭了重复 permutation replay，因此报告中的 permutation 字段为空；冻结的 v0.9.23
正式 OOF 已单独完成 7,200/7,200 permutation deterministic 检查。

## 下一步训练协议

下一模型不得再输出彼此独立的 veto：

1. 孤立组件直接复用 v0.9.23 score，不进入新模型。
2. 多节点组件枚举所有可行 matching；当前 23,704 个组件多数只有 7–10 个 matching，最大 3,776。
3. 共享 anchor 的 pair 通过至少两轮消息传递交换证据。
4. loss 对整个 matching 做 log-sum-exp / structured ranking，而不是逐 pair BCE。
5. 推理只允许从 v0.9.23 已激活的边中删除，不允许 rescue，先守住 M2 和零误伤边界。
6. 首个门槛目标是 cross ≤ 8、M2 ≥ 99.8%、pairable exact ≥ 98%，最终目标仍为 cross 0。
